How AI Agents Pay Each Other with x402: HTTP 402, USDC, and Per-Call Settlement

AI agents increasingly call APIs owned by someone else — search, data, letter generation, analysis. When the caller is software, a monthly invoice and a dashboard signup are friction the machine cannot complete. x402 is an open standard for internet-native payments that fixes this: the API responds with HTTP 402 "Payment Required", the agent pays, and the call completes — all inside one HTTP conversation.

The four pieces

- Client — the agent (or the framework wrapping it) making the call.

- Resource server — the API selling access per call.

- Facilitator — an optional third party that verifies and settles the payment on behalf of the server.

- Payment mechanism — the scheme and asset. The common default is exact EVM with USDC, a dollar stablecoin, on networks like Base.

The flow, step by step

1. The client calls the API without payment. The server does not execute the resource; it returns a 402 with a PaymentRequired object describing exactly what a valid payment looks like.

2. The client constructs the payment. It picks one entry from the server's accepts[] array, signs the corresponding payment payload (for EVM exact, an EIP-3009 transferWithAuthorization against USDC), and re-sends the request carrying the payload in the transport-defined header.

3. The facilitator verifies. The resource server (or its middleware) hands the payload plus its own payment requirements to the facilitator's /verify endpoint. This is read-only: signature, amount, asset, recipient and expiry are checked without moving funds.

4. The resource executes, then the facilitator settles. In the default authorization flow, settlement happens only after the resource completes successfully — the buyer never pays for a failed call. /settle broadcasts the on-chain USDC transfer and returns a settlement proof.

5. The server returns the paid response, and the settlement proof rides back to the client so the agent can account for what it spent.

What the 402 actually looks like

This is the shape from the x402 v2 specification (values from the spec's own example):


{
  "x402Version": 2,
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Access to premium market data"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:84532",
      "amount": "10000",
      "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
      "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "maxTimeoutSeconds": 60,
      "extra": { "name": "USDC", "version": "2" }
    }
  ]
}

Note what is *not* there: no account creation, no API key, no invoice. The accepts[] entry is machine-readable enough that an agent can decide — from the scheme, network, amount and asset alone — whether to pay.

Why agents change the pricing model

A human developer tolerates signup friction because the relationship lasts months. An agent may need one call, once, from a wallet holding a few dollars. Per-call settlement with USDC means:

- No minimum commitment — the agent pays exactly for the calls it makes.

- Composable trust — the payment proof is cryptographically checkable, so the agent can verify it was charged the advertised amount.

- Fail-safe ordering — in the default flow, funds move only after the resource succeeds.

Takeaway

x402 turns "HTTP 402" from a curiosity into a working payment rail for machine-to-machine API calls. For agent developers, adopting it means your agents can buy from any x402-enabled API without a human in the loop; for API owners, it means agent traffic can finally pay for itself, one call at a time.
