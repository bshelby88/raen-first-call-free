Turning Any API into a Per-Call Paid API That Settles in USDC on Base

If you run an API, agent traffic is either already knocking at your door or will be soon. Agents do not fill out signup forms, paste API keys into a dashboard, or pay monthly invoices with a card. The x402 standard gives you a way to charge them per call — in USDC on Base — without changing what your API does.

Why per-call beats API keys for agent traffic

API keys assume a relationship that does not exist yet. Keys require a signup flow, a billing contact, and a payment method on file. An autonomous agent with a wallet and a task has none of those. Per-call payment meets the agent where it is: it can pay, immediately, for the one call it needs.

Invoices assume predictable volume. Monthly plans force you to guess tiers and force buyers to overpay for headroom. Per-call pricing scales perfectly with demand — zero calls cost zero dollars, ten thousand calls cost exactly ten thousand times the price.

Per-call matches agent economics. Agents budget per task. A call that costs $0.01–$1.00 is a rounding error next to the LLM tokens spent deciding to make it. Charging per call keeps your API inside that budget instead of triggering a procurement conversation.

What your server has to do: the 402

The entire opt-in is one response shape. When an unauthenticated request arrives, return a 402 with a PaymentRequired object. From the x402 v2 specification:


{
  "x402Version": 2,
  "resource": {
    "url": "https://api.example.com/letters",
    "description": "FCRA dispute-letter generation"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:84532",
      "amount": "7500",
      "asset": "USDC contract address",
      "payTo": "your wallet address",
      "maxTimeoutSeconds": 60
    }
  ]
}

The amount is in atomic token units — "7500" is $0.0075 of a 6-decimal USDC. The accepts[] entry tells the agent everything it needs: which scheme, which network, how much, to whom, and how long it has.

What changes in your handler after settlement

With an x402 SDK, the middleware does most of the work and your handler changes are minimal:

1. Wrap your routes with the payment middleware, declaring which routes are paid and their accepts[].

2. Before your handler runs (in the default authorization flow), the payment payload is verified against your own requirements — the middleware passes your matching requirements, not the client's copy, to the facilitator's /verify. This binding matters: a client that rewrites the terms must fail here, not at your bank.

3. Your handler executes exactly as before, returning whatever it always returned.

4. After success, /settle moves the USDC on-chain and the settlement proof is attached to the response.

The one real design decision is idempotency: decide what happens if the same request retries after settlement, and make your paid work idempotent per payment proof.

Honest state of play

Agent-paid APIs are early. Traffic volumes today do not make anyone rich, and facilitator coverage varies by network. But the cost of adding x402 to an existing API is small, the revenue model is strictly additive (per-call on top of whatever keys you already sell), and every agent framework moving toward wallet-native payments increases the value of being listed and payable now.

Takeaway

Turning an API into a per-call paid API is a middleware change, not a business-model redesign: declare your price in an accepts[] entry, let the SDK verify and settle USDC on Base, and keep your handler untouched. For agent traffic, that is the difference between an abandoned signup form and a paid call.
